You were right to push back. I read the app, the coach function, the database policies and the service worker before writing this. There is one thing I would fix today, one live bug, and a handful of guardrails missing.

First, what I got wrong

“No framework, no build step, no bundler” was jargon, and worse, it pointed at the wrong thing. Those three words describe tooling, and your app genuinely does not need any of it — but I wrote it as though simple meant unguarded, and that is not what good simple code looks like.

What simple should actually mean here: the code is easy to read and easy to change, and it still checks its work. Errors are caught and shown. Inputs are validated. Anything non-obvious carries a comment saying why. Failures are visible rather than silent.

Judged that way, this app is not over-engineered. In the places that matter it is under-engineered.

Two of those jargon words are worth one plain sentence each, because they are actually good decisions you made. No build step means the file you edit is the file that runs — nothing has to be compiled or published first, which is why a change can reach your phone in seconds. No framework means no large third-party library sitting between your code and the browser, which for an app this size is the right call. Both stay.

What is already right

Worth saying plainly, because the findings below are blunt.

✓
The architecture suits the problem. Two people, no login, one screen at a time. A static page plus a database plus a logic file you can swap without a deploy is a genuinely smart fit — most people would have reached for something ten times heavier.
✓
Schema changes are tracked. Eight named migrations, in order, from the initial schema through to the paused-exercise state. That is real discipline and most projects at this stage do not have it.
✓
The API key is handled correctly. The Anthropic key lives in the function’s server-side secrets and the coach runs on the server. It is never in the page. That is exactly right, and it is the mistake this kind of project usually makes.
✓
The coach cannot act on its own. Proposals are capped at five, nothing applies until you tick it, and the budget logic degrades to a cheaper model before it stops. Good safety design.
✓
The per-date reset logic is carefully thought through. Checklists, logs and overrides all key on a date, and the template stays clean. That is the hard part of a daily planner and it is right.

What needs fixing

Ordered by what I would do first.

F1Fix firstThe database is open to anyone with the link
Every table has a rule that says “anyone may read, write and delete anything”. The key the app uses to talk to the database is in the page source, where anyone can read it. So the private link is not a lock — it only decides which person the app shows you. Anyone who ever gets the URL could, with a little effort, read or wipe both your plan and Gong’s, including every logged set and every notification subscription.

Your actual risk today is low — nobody has the link but you two. But the cost if it happened is everything, and the fix is cheap. I would not add a second person to this app until it is closed.
All 12 data tables carry policies of the form: SELECT / INSERT / UPDATE / DELETE to role "anon" USING (true) "USING (true)" means: no condition. Always allowed.
The fixTwo options. The thorough one: stop letting the browser talk to the tables directly, and put reads and writes behind a small server function that takes the private link and uses a privileged key — the link then becomes a real credential. The quick one, worth doing regardless and today: remove delete permission entirely from the browser, and scope every write to the person the link identifies. Deleting is the only irreversible operation in the app.
F2Fix firstNothing checks whether a save actually worked — and one already fails
Roughly twenty places in the app write to the database. Not one of them looks at whether the write succeeded. The screen redraws as though it did. If the network drops, or a permission blocks it, the app shows you the new value and the database never received it. You would find out days later, or never.

This is not hypothetical. The workout table — the routines themselves — is the one table that was never given write permission for the browser. Creating a new routine, renaming one, and changing its focus are all denied by the database right now, and because nothing checks, they fail in complete silence.
exercise / block / goal tables: SELECT INSERT UPDATE DELETE workout table: SELECT only But app.js calls: sb.from("workout").insert(...) → denied, silently sb.from("workout").update(...) → denied, silently
The fixWorth testing yourself in a minute: rename a routine, reload, and see whether the name held.

Then: one small wrapper that every write goes through. It saves, checks the result, and on failure puts the screen back the way it was and shows a short message. Around fifteen lines, written once, and it removes an entire category of bug from every stage that follows. This is the clearest example of a guardrail that is not over-engineering — and the missing permission gets added at the same time.
F3Fix firstA quote mark in a name breaks the editor
The function that makes text safe to put on screen handles three dangerous characters but not quote marks. Those values then get placed inside HTML attributes, where a quote mark ends the attribute early and the rest of the name spills into the page as markup. Name an exercise 3" band pull and the editor breaks.
esc() replaces: & < > esc() misses: " ' and the result is used as: value="${esc(e.name)}"
The fixTwo more replacements in that one function. A minute of work, and it stops a whole family of odd bugs that would otherwise look random.
F4Worth fixing“Today” is decided in two different places
The app asks the phone what day it is. The reminder service asks your saved timezone. Those two already disagreed once — that is what put a 1pm lunch reminder at 1am. It was patched by syncing the timezone, but the underlying split is still there. Travel, or a session that runs past midnight, and a tick can land on a different date than the reminder believes.
The fixOne function that answers “what date is it for this person”, used by the app and the reminder service alike. Pick the profile timezone as the single rule, since that is the one that survives travel.
F5Worth fixingThe app cannot update itself
This is why “close and reopen the app” is a step in every release note. The offline cache is named once and never renamed, and the logic file is requested at a fixed address, so the phone has no way to know a new version exists. It is a workaround standing in for a missing mechanism.
The fixStamp a version on the logic file’s address and rename the cache each release. The app then notices the change and refreshes itself, and the manual step disappears.
F6Worth fixingWhen something fails, nobody finds out
There is no message on screen, no log anywhere, no record. On a phone, with no console open, a failure is completely invisible. Combined with F2 this is how data goes missing without anyone noticing.
The fixA short message on screen when a save fails is enough for one user — you do not need a monitoring system. The point is that silence stops being the failure mode.
F7Worth fixingYour data has no backup
The app’s code gets copied before every change — that is in the build order. Your plan, your routines, your logs and your goals do not. One bad command, or F1 going wrong, and there is no way back. Months of logged sessions are the thing the coach’s value is built on.
The fixA scheduled job once a week that writes a snapshot of everything to a file in storage. Small, boring, and the thing you will be glad of exactly once.
F8PolishThe whole screen redraws on every tap
Ticking one checkbox rebuilds the entire page and re-attaches every handler. At this size that is fine and I would not change the approach — it is simple and it works. But it loses your scroll position, which will be much more noticeable on the new workout screen where you are thirteen exercises down.
The fixKeep the full redraw. Remember the scroll position and restore it afterwards — a few lines, and the screen stops jumping.
F9PolishOne 57,000-character file with no signposts
Not a crisis, and splitting it into many files would cost more than it saves. But there are no section markers, and the entire stylesheet is a single text block inside the same file as the logic.
The fixSection banners and a short index comment at the top, and move the stylesheet to its own file alongside the logic. Both are the same kind of change: nothing behaves differently, everything gets easier to find.

The rule, rewritten

Replacing what I wrote badly the first time. This now sits at the top of the build order:

Write it simple, and write it safe.

Keep it plain — ordinary functions with clear names, no compile step, no heavy libraries, no abstraction invented before it is needed. A longer obvious function beats a shorter clever one.

And check the work — every save is checked and reverts visibly if it fails; input is validated where it enters; text is escaped properly; permissions are scoped to the person; anything irreversible asks first; anything non-obvious carries a comment explaining why.

Simple is about how much there is to understand. It was never about leaving out the parts that keep it correct.
